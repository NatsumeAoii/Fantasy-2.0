# Aetheris Character Forge

A deterministic fantasy RPG character generator built as a React single-page app. A character can be regenerated from the same seed and name, then explored through profile, lore, world, mechanics, skills, inventory, vault, stable, and bestiary-oriented views.

The app is frontend-only. There is no backend service, database, Docker setup, or committed environment file in this repository.

**Live:** [https://natsumeaoii.github.io/Aetheris-CharGen/](https://natsumeaoii.github.io/Aetheris-CharGen/)

---

## Quick Start

Prerequisites: [Node.js](https://nodejs.org/) 22+ and npm.

```bash
git clone https://github.com/NatsumeAoii/Aetheris-CharGen.git
cd Aetheris-CharGen
npm ci
npm run dev
```

Vite prints the local development URL after startup — typically `http://localhost:5173/`.

## Configuration

No required environment variables exist in this codebase.

<details>
<summary><strong>Build and runtime details</strong></summary>

- Routing uses TanStack Router with **hash history** — production URLs are hash-based (`/#/character/seed-here`).
- `src/routeTree.gen.ts` is generated by TanStack Router's Vite plugin and must not be edited manually.
- `vite.config.ts` sets `base: './'` for static hosting and GitHub Pages compatibility.
- `vite.config.ts` defines manual chunks for large generated-data areas to keep initial bundle lean.
- `vite.config.ts` injects `VITE_APP_VERSION` at build time from `package.json` version.
- Generated characters are not persisted as full records — the app reconstructs them from route seed/name data.
- Local UI preferences (theme, density, motion, scale, panel sub-tabs) are stored in `localStorage` under keys prefixed `aetheris-`.

</details>

## Architecture Overview

### Generation Flow

Routes call the character store (`src/store/characterStore.ts`). The store dynamically imports `src/lib/generator.ts`, which constructs the character using domain engines in `src/logic/`.

Generation is **seed-driven and deterministic** — the same seed + name always produces the same character. All randomness during generation comes from a seeded PRNG in `src/lib/randomUtils.ts`.

```text
Route (seed from URL) → characterStore.generate() → dynamic import generator.ts
  → CharacterGenerator orchestrates domain engines:
     StatEngine, LoreEngine, IdentityEngine, WorldEngine, MagicEngine,
     MechanicsEngine, BestiaryEngine, BackstoryEngine, InventoryEngine,
     CharacterExpansionEngine
  → Returns frozen Character object → store state update → UI re-renders
```

### UI Flow

The main character experience is composed from `CharacterShell` (layout grid with identity rail + content area) and `TopTabs` (accessible tab navigation). Heavier panels are lazy-loaded with `React.lazy` and `Suspense`.

### State Management

- **`characterStore`** — Core character state, generation trigger, inventory moves, tab selection.
- **`historyStore`** — Recent characters, favorites, comparison (persisted to localStorage).
- **`preferencesStore`** — Theme, density, motion, scale, generation preferences (persisted to localStorage).
- **`eventBus`** — Typed pub/sub for cross-store communication without coupling.

### Data Architecture

Static data lives under `src/data/` as TypeScript modules. These are hand-curated datasets that feed generation engines — they are never modified at runtime. The project uses a **6-tier** static data system (Common through Mythic) and an **8-tier** runtime rarity system (adding Divine and Artifact for extreme-level procedural generation).

Configuration lives under `src/config/` and defines how data is consumed: tier ranges, rarity maps, probabilities, soft caps, and generation constraints.

## Testing

Tests use Vitest with jsdom and React Testing Library. Configuration lives in `vitest.config.ts`; setup in `test/setup.ts`.

```bash
npm test              # Run once
npm run test:watch    # Watch mode
npm run test:coverage # With coverage report
```

Test directory structure mirrors `src/`:

- `test/logic/` — Engine unit tests (stat, inventory, lore, pool, expansion)
- `test/components/` — Component behavior tests (panels, layout, UI controls)
- `test/routes/` — Route integration tests
- `test/store/` — Store state and event bus tests
- `test/lib/` — Utility function tests
- `test/hooks/` — Hook behavior tests

When contributing, add tests for generation behavior changes, inventory movement, route behavior, persisted tabs, and keyboard interaction.

## Build and Deploy

```bash
npm run build
```

Production output goes to `dist/`. The build runs TypeScript type-checking first, then Vite bundling.

**GitHub Pages deployment** is configured in `.github/workflows/deploy.yml`. On pushes to `main` or manual dispatch: CI uses Node 22, runs `npm ci` → `npm run lint` → `npm run build`, then uploads `dist/` to Pages.

## Contributing

See [CONTRIBUTING.md](CONTRIBUTING.md) for detailed guidelines.

Quick summary:
- Keep React UI in `src/components/`, hooks in `src/hooks/`, generation/business logic in `src/logic/` or `src/lib/`.
- Do not edit `src/routeTree.gen.ts` manually.
- Keep generated-data files deterministic and side-effect free.
- Use existing shared controls before creating new variants.
- Run `npm run lint` and `npm test` before submitting changes.
- Avoid adding dependencies unless the current stack cannot handle the task.

## Troubleshooting

<details>
<summary><strong>Direct URL doesn't resolve</strong></summary>

The app uses hash history. Use the hash route form: `/#/character/my-seed`.

</details>

<details>
<summary><strong>Need a different dev port</strong></summary>

```bash
npm run dev -- --port 5174
```

</details>

<details>
<summary><strong>Tunnel host blocked by Vite</strong></summary>

Add your tunnel hostname to `server.allowedHosts` in `vite.config.ts`. Do not commit personal tunnel hostnames.

</details>

<details>
<summary><strong>TypeScript or Vite fails on older Node</strong></summary>

Use Node 22 to match CI. The `engines` field in `package.json` requires `>=22.0.0`.

</details>

<details>
<summary><strong>Routes appear stale after route file changes</strong></summary>

Restart the dev server so the TanStack Router Vite plugin regenerates `src/routeTree.gen.ts`.

</details>

<details>
<summary><strong>Tests fail with import errors</strong></summary>

Run `npm ci` to ensure dependencies match `package-lock.json`. Tests use a separate `vitest.config.ts` (not `vite.config.ts`), so Vite plugin differences are expected.

</details>

## Q&A

<details>
<summary><strong>Why is there no backend or database?</strong></summary>

Characters are fully generated client-side from a deterministic seed. The same seed always produces the same character — no storage needed. This makes the app deployable as a static site with zero infrastructure.

</details>

<details>
<summary><strong>What does "deterministic" mean here?</strong></summary>

Given the same seed string and character name, generation produces byte-for-byte identical output every time. All randomness comes from a seeded PRNG (`src/lib/randomUtils.ts`). This enables shareable character URLs — anyone with the same URL sees the same character.

</details>

<details>
<summary><strong>What's the difference between the 6-tier and 8-tier systems?</strong></summary>

Static data files (`src/data/`) use 6 tiers: Common → Uncommon → Rare → Epic → Legendary → Mythic. The runtime config (`src/config/inventoryConfig.ts`) adds 2 procedural-only tiers (Divine, Artifact) for extreme-level characters (3000+). Tiers 7–8 have no static data entries — they are generated procedurally at runtime.

</details>

<details>
<summary><strong>How do I add new generated data?</strong></summary>

Add data files to the appropriate domain folder under `src/data/`. Follow the conventions in `.workRules/dataRules.md`: 6-tier system, snake_case IDs, Title Case names, 150-char max descriptions, no D&D terminology. Update the barrel `index.ts` in that domain. If the data needs special chunking, add it to `vite.config.ts` manual chunks.

</details>

<details>
<summary><strong>Why hash routing instead of browser history?</strong></summary>

The app deploys to GitHub Pages as a static site. GitHub Pages serves `index.html` only at the root — it doesn't support catch-all routing for arbitrary paths. Hash routing (`/#/path`) works without server configuration.

</details>

<details>
<summary><strong>Where are UI preferences stored?</strong></summary>

In `localStorage` under keys `aetheris-preferences` (theme, density, motion, scale, generation prefs) and `aetheris-history` (recent characters, favorites). These are managed by Zustand persist middleware in the respective stores.

</details>

<details>
<summary><strong>What's the _legacy/ folder?</strong></summary>

The original vanilla HTML/CSS/JS version of the character generator, preserved for reference. It is gitignored and not part of the active build, test suite, or deployment.

</details>

<details>
<summary><strong>How do manual chunks in vite.config.ts work?</strong></summary>

The `manualChunks` function splits large data files and icon libraries into separate bundles so they only load when needed. Each domain (bestiary, inventory items, character data, etc.) gets its own chunk. This keeps the initial page load fast since most data is only needed after a character is generated.

</details>
